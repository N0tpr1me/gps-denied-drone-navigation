# Decisions

One row per decision. Change a row only in its own PR, and say why in the PR.
Full reasoning: the Structure Hold build plan and execution plan (project docs, 21 Oct 2026).

## Product and scope

| Decision | Status | Date | Why / what would change it |
| --- | --- | --- | --- |
| Build one onboard PX4 flight mode, "Structure Hold": hold and 5 m passes 1 to 3 m from a structure in gusts, no GPS, robust to bad position estimates | Decided | 2026-10-21 | Product strategy doc |
| Out of scope: VIO/SLAM, mapping, planning, obstacle avoidance, ground station, vision in the policy | Decided | 2026-10-21 | Use the drone's existing position source; accept position + covariance |

## Technical

| Decision | Status | Date | Why / what would change it |

| Learned outer loop: body rates + collective thrust at 100 Hz over PX4's stock rate controller; MLP ~10k params, 3-step history, asymmetric critic | Decided | 2026-10-21 | Rate interface is the bottleneck at Gate 2 → try direct motor commands |
| RL library: rsl_rl PPO, version pinned in `pyproject.toml` when training code lands | Decided | 2026-10-21 | Only if rsl_rl lacks something needed |
| Simulator: Isaac Lab native quadrotor task (direct workflow), not Aerial Gym | Decided | 2026-10-21 | Adopted by default: Zain asked to complete Phase 0 and did not object. Falls back to the batched PyTorch sim if Isaac Lab is not training the stock task within 5 working days on the server |
| PX4 integration: onboard C++ module from day one, registered as a named mode (no commander patch, confirmed by PR #9), built into `px4_sitl` first | Decided | 2026-10-21 | Adopted by default: Zain asked to complete Phase 0 and did not object |
| Test airframe: ModalAI Starling 2; fallback Holybro X500 V2 + Pixhawk 6C; order by March 2027 | Decided | 2026-10-21 | Adopted by default: Zain asked to complete Phase 0 and did not object. Switch to the fallback if ModalAI's build flow will not take the module within 2 weeks |
| Develop against a batched PyTorch quadrotor ("mock", `envs/sims/torch_quad.py`) until the GPU server exists; Isaac Lab plugs in behind the same seam (thrust, body torque, external force in; `QuadState` out) | Decided | 2026-10-21 | GPU server access comes later; specs unknown |
| PX4 release pinned at Phase 0 (not Phase 2) and held through Gate 3; tag recorded here by the SITL image task | Decided | 2026-10-21 | A baseline tuned on one release is not fair on another. Moving the pin means re-tuning the baseline |
| PX4 pinned tag: **v1.17.0** (`sim2real/docker`: Ubuntu 24.04, Gazebo Harmonic, MAVSDK-Python 3.17.4) | Decided | 2026-10-21 | Latest stable release at pin time; builds from source on arm64 and amd64. Moving it means re-tuning the baseline |
| Shared core code is NumPy + PyYAML only, Python 3.10 to 3.12; PyTorch only in the batched sim and training | Decided | 2026-10-21 | Must import in Isaac Lab, the SITL image and the Mac |
| One run on one GPU at a time; `training/launch.py` gates on `nvidia-smi`, refuses >1 GPU or >1 h without `--approved` | Decided | 2026-10-21 | Compute plan; project rules |
| Disturbance model is stateless: turbulence is a seeded sum of sinusoids with a Gauss-Markov spectrum, so force is a pure function of params, time, position and velocity (`envs/disturbance/`) | Decided | 2026-10-21 | Same wind in every simulator regardless of step size or call rate. A stateful filter would only be needed if the fan-rig fit shows a spectrum the sinusoids cannot match |
| Metrics: one scorer for sim, SITL and real logs (`eval/metrics.py`, defined in `docs/metrics.md`); scored on TRUE position (ground truth / mocap), never the EKF estimate; 100 Hz resampling; recovery = from gust end to within 10 cm held 1 s; contact radius 0.25 m until the airframe is fixed | Decided | 2026-10-21 | Changing a default changes every result, so it changes only with a row here |
| Mock simulator airframe is a placeholder 5-inch-class quad (0.8 kg, 16 N max thrust, 0.02 s motor lag) in `envs/sims/torch_quad.py`; the rate loop in the env is a PX4-shaped rate PID with PX4 default gains | Placeholder | 2026-10-21 | Replaced by the chosen airframe's numbers and its tuned `MC_*RATE_*` params at M1 |
| Structure Hold env: policy at 100 Hz commands body rates and thrust; the wall is the plane x = 0 (structure frame = world frame); reward and termination on the true state, the policy sees only the corrupted estimate (`envs/structure_hold/`) | Decided | 2026-10-21 | Matches the onboard module's output (rate setpoints) and the plan's seam; keeps one frame until a second structure shape is needed |
| Gazebo wind adapter is a C++ world system plugin (`sim2real/gazebo/plugin`, `StructureHoldWind`) that evaluates a C++ copy of `envs/disturbance/core.py` from a params file Python writes, not a Python bridge over gz-transport | Decided | 2026-10-21 | The force is computed and applied inside the same physics step (zero lag, no transport jitter), runs with no Python process alongside Gazebo, and the per-step trace is exact. Gazebo's `ApplyLinkWrench` topics accumulate persistent wrenches and need a separate clear message, and its odometry velocity is a 10-sample rolling mean, so a bridge would add lag and ordering races. Cost: a second copy of the model, held equal by the parity test (`sim2real/gazebo/parity.py`, 1e-9 N). Revisit if the model grows state or a torque term that is awkward to mirror in C++ |
| Training: rsl_rl PPO pinned at `rsl-rl-lib==5.5.1` (its VecEnv and config layout changed between majors); the policy is a 64x64 ELU MLP (about 8k parameters) on the last 3 observations stacked oldest first, with a critic that also sees the true state and wind (asymmetric actor-critic); exported as `policy.onnx` with a free batch size plus `policy.json` describing the input layout and action scaling (`training/`) | Decided | 2026-10-21 | The onboard module keeps the same 3-step buffer; a recurrent policy would need a different export and C++ runtime. Re-pin only in its own PR after the smoke and parity tests pass |
| Structure Hold reward is bounded per step (alive 2.0 minus saturating penalties: position 1.5 x (1 - exp(-err / 1 m)), toward-wall 0.5 clipped at 1 m, speed and rate clipped) plus a tilt penalty beyond 45 deg, so a live step always beats a crash; training uses 5x the standard jump and dropout rates (0.1 Hz) while every reported score uses the standard 0.02 Hz | Decided | 2026-10-21 | With unbounded penalties a drone drifted past ~1 m during a dropout earned less per step than nothing and learned to tilt over to end the episode (77 % of v0's crashes were while stale). Revisit the weights when the real VIO numbers replace the placeholder corruption (T7) |
| Estimate injection into PX4: a Python bridge in the SITL image reads Gazebo's `pose/info` (50 Hz), runs `envs/estimate` and sends MAVLink ODOMETRY (local NED position + velocity, VIO estimator type, no attitude, no covariance) to PX4's second onboard link; EKF2 on `EKF2_EV_CTRL 7`, `EKF2_HGT_REF 3`, `EKF2_GPS_CTRL 0`, `SYS_HAS_GPS 0` (`sim2real/estimate_bridge/ekf2_ev.params`); not uXRCE-DDS, not a Gazebo odometry publisher | Decided | 2026-10-21 | ODOMETRY is the path a real VIO companion uses (ModalAI, MAVROS), needs nothing beyond pymavlink and the gz Python bindings already in the image, and is one UDP hop inside the container: EKF2 fused every sample the bridge sent (4799 of 4808 in the clean reference, 0 rejected). uXRCE-DDS would need the agent, ROS 2 message types and a second clock domain; a Gazebo OdometryPublisher cannot carry the corruption. Samples are stamped on arrival (no TIMESYNC reply), so the corruptor's delay is real latency compensated only by the constant `EKF2_EV_DELAY`, as on a VIO without clock sync. During a dropout nothing is sent. The bridge sends `SET_GPS_GLOBAL_ORIGIN` once, as a VIO companion does, because PX4's Hold mode (the commander's idle mode and the mode after an auto takeoff) requires a global position even when every position comes from vision; without it arming is refused ("Ready for takeoff" refers to Takeoff mode only) |
| Estimate corruption defaults (`envs/estimate/core.py`, shared by training and the SITL benchmark): delay 50 to 150 ms per episode; position noise 0.02 m, velocity noise 0.05 m/s; bias walk 0.01 m/sqrt(s) capped at 0.3 m; jumps 0.1 to 2 m at 0.02 Hz decaying over 5 s; dropouts 0.2 to 3 s at 0.02 Hz | Decided | 2026-10-21 | Delay: a 30 Hz stereo-inertial pipeline (ModalAI qVIO class) delivers a frame 1 to 3 frame periods after capture plus transport, and PX4 documents `EKF2_EV_DELAY` as a constant to be tuned per setup, so the range is centred on 100 ms (= `EKF2_EV_DELAY` in `ekf2_ev.params`) with the jitter left uncompensated. Noise: ORB-SLAM3 stereo-inertial reports 3.6 cm average error on the EuRoC drone sequences and VINS-Mono 0.19 to 0.40 m ATE on the same set; 2 cm per-sample jitter sits below the stereo figure because the slow part of that error is the bias walk, whose cap (0.3 m) is the VINS-Mono band. `EKF2_EVP_NOISE` / `EKF2_EVV_NOISE` defaults are 0.1 m and 0.1 m/s, so the EKF is told less than it gets, as in a stock setup. Jumps: relocalisation after a loop closure or a tracking reset, 0.1 to 2 m per the plan, one per 50 s on average so a 20 s training episode sees one in roughly a third of episodes. Dropouts: tracking loss on a textureless wall, kept below `EKF2_NOAID_TOUT` (5 s) so stock EKF2 survives them by dead-reckoning; longer losses are a failsafe case, out of scope for the hold task. Replace with measured values from the test airframe's own VIO when it flies |
| Dropout-length curriculum during PPO (`params.curriculum`: cap dropouts at 0.5 s at the start, grow linearly to 3 s over the first 60 % of iterations) stays OFF by default | Decided | 2026-10-21 | One logged run (`20261021-233043_structure_hold_ppo_s0_7503396`, scored by `20261021-235204_structure_hold_eval_candidate_s1_f77cc79`) came out worse than policy v1 on the same 3 seeds x 2048 episodes: crash 9.6 % +/- 0.4 vs 6.1 % +/- 0.3, p95 0.59 m vs 0.48 m. Training crash rate climbed as the cap grew (the policy had learned to trust the estimate), so the easy start cost more than it gave. Revisit with more iterations or a slower ramp on the GPU server; the hook (`StructureHoldEnv.set_dropout_max_s`) stays |
| Actor observation history must cover the estimate delay range: with the 50 to 150 ms delay default (PR #14) the 3-step (30 ms) history of policy v1 cannot identify the delay, which changes per episode | Proposed | 2026-10-22 | Evidence on 3 seeds x 2048 episodes and single-seed 256-episode scores (`experiments/LOG.md`): v1 rescored under the new default crashes 32.6 % (PD 4.0 %); retraining the v1 recipe on it gives p95 0.87 m, crash 18.6 % (PD 0.69 m, 5.1 %); a 15-step history (`structure_hold_ppo_h15.yaml`, 23.7k actor params) gives p95 0.72 m, crash 14.0 % after 1500 iterations and was still improving at the end (31 min on 4 CPU cores). Becomes Decided once a longer 15-step run beats the PD on both numbers; the ONNX contract (`policy.json` input.history) carries the length either way |
| Actor history 15 steps (150 ms) is the training default and policy v2 (`training/policies/structure_hold_v2`) the released policy; long runs are chained with `params.resume` (two 30 min runs) rather than one over the hour limit | Decided | 2026-10-22 | 15-step history continued to 3000 iterations (runs `20261022-002309` + `20261022-005714`) scores p95 0.54 m vs PD 0.82 m and crash 8.4 % +/- 0.4 vs 4.0 % +/- 0.3 on 3 seeds x 2048 episodes under the 50 to 150 ms delay default (`20261022-012927`); v1 crashes 32.6 % there. The crash rate is still above the PD, so the next work is on crashes, not the hold. Revisit the history length if the PX4 module cannot afford 300 inputs at 100 Hz |
| Reward adds a speed penalty while the estimate is stale (`RewardWeights.stale_vel` 0.3 on top of `vel` 0.05, bounded at 5 m/s) | Decided | 2026-10-22 | Diagnosis of policy v2 on 2048 episodes: 59 % of its crashes happen during a dropout, 77 % are leaving the 3 m box, at 2.7 m/s mean speed vs 1.3 m/s for the PD and with little wind (1.2 N): the policy keeps chasing a frozen estimate at speed. The PD crashes 27 % stale. The term asks for slowing down, not stopping; remove it if a policy trained with it no longer beats the PD on p95 |
| `RewardWeights.stale_vel` stays 0 (off); the frozen-estimate crashes are not fixable from the reward alone | Decided | 2026-10-22 | Two runs with `stale_vel` 0.3 under the 50 to 150 ms delay: fine-tuning policy v2 (`20261022-014045`) left its crashes unchanged (9.3 %, 2.7 m/s at crash); training from scratch with 10x the dropout rate for 3000 iterations (`20261022-021354` + `20261022-031613`, scored by `20261022-034542`) gave p95 0.70 m and crash 9.9 % +/- 0.4 vs v2 0.54 m / 8.4 %. During a dropout both position and velocity are held, so a controller acting on them flies off at constant speed; the PD does too, only slower. What would fix it: a dead-reckoned velocity from the estimator during dropouts (IMU integration, `envs/estimate`, mirrors what EKF2 does) or a classical brake-and-hover fallback in the module when the estimate is stale beyond ~1 s. Either is a product decision for Zain |
| Estimate dropouts dead-reckon by default (`EstimateCorruptionConfig.dropout_mode = "dead_reckon"`, acceleration bias N(0, 0.3 m/s^2) per axis drawn per dropout, so velocity drifts by bias x age and position by bias x age^2 / 2); `"hold"` (frozen output) stays selectable | Decided | 2026-10-22 | With a frozen velocity no controller can brake during a dropout (policy v2 and the PD both fly off; see the `stale_vel` row). A real EKF keeps integrating the IMU when vision stops, so the reported velocity stays usable and drifts slowly: this is what the module will see on the aircraft. Every result before this row was measured with `hold`; set `estimate.dropout_mode: hold` to reproduce them. Policies are retrained and the PD rescored under the new default from here on |
| Policy v2 stays the release; the retrain of its recipe on the dead-reckoning estimate is not released | Decided | 2026-10-22 | v2 (trained on `hold`) rescored under `dead_reckon` on 3 seeds x 2048 episodes (run `20261022-050718`): p95 0.51 m, crash 6.7 % +/- 0.3 (was 0.54 m, 8.4 % under `hold`); PD under the same estimate 0.83 m, 4.6 % +/- 0.3. The same recipe retrained from scratch on `dead_reckon` (runs `20261022-035818` + `043117`, 3000 iterations as two resumed 30 min runs, checkpoint 2750) scored 0.59 m, 7.3 % +/- 0.3 (run `20261022-050300`): worse than v2 on both numbers. The estimator change alone closed part of the crash gap (dropouts no longer freeze the velocity), the retrain added nothing. Crash rate is still above the PD; the remaining lever is a classical brake-and-hover fallback in the PX4 module after a long dropout, or more training on the GPU server. |
